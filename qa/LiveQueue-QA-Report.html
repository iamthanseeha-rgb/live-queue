LiveQueue QA Findings

The core flow works: sign up, get a desk, tap +1 Next Token, and the public screen updates. But billing and token balances are fully controlled by the browser, and two devices on one desk overwrite each other. Both are revenue problems, not cosmetic ones. Fix those two before spending on ads.

CriticalPAY-01Recharges have no Razorpay order and no signature check, so the browser credits tokens itselfBillingReproduced

The checkout opens without an order_id. After payment, the browser adds the tokens to usage directly. No server ever confirms the payment. Razorpay's docs say payments made without an order_id can't be captured and are refunded automatically. That means real customers may be refunded within about 3 days and keep their tokens. The payment ID is never stored, so you can't reconcile payments either. .env.local also holds a rzp_test_ key, so check which key the live Vercel build uses.

Steps to reproduce
  1. Dashboard → Recharge → pick any pack.
  2. Complete payment (test mode).
  3. Open the Razorpay dashboard: the payment shows authorized, not captured, and has no order.
  4. Tokens are already in the balance.
What the test saw
The test stubbed checkout with a fake payment ID pay_FAKE, and the balance went from 100 to 5,100. The checkout options had order_id = undefined.
Fix
Add a Supabase Edge Function create-order that takes the price from a server-side pack table. Pass the returned order_id to checkout. Credit tokens only from a payment.captured webhook, or after a server-side HMAC signature check, inside one DB transaction. Record every payment in a payments table with UNIQUE(razorpay_payment_id) so a retry can't credit twice.

CriticalSEC-01Any logged-in host can give themselves unlimited tokensSecurityCode review

The app's own code writes usage.remaining_tokens from the browser (on every Next tap and every recharge). For that to work, your database must let a logged-in host UPDATE their own usage row, with any value. The anon key and URL ship inside the public JS bundle, so one line in DevTools sets the balance to anything. The browser also inserts the admin row with status: 'Active', so account status is client-controlled too, unless RLS stops it.

Steps to reproduce
  1. Sign in, open DevTools → Console.
  2. Create a Supabase client with the URL and anon key from the bundle (or reuse the app's session).
  3. update usage set remaining_tokens = 999999 where admin_id = me via .from('usage').update(...).
  4. Reload: the balance shows 999,999.
What the test saw
Confirmed from the code design: advanceQueue (L403–409) and the recharge handler (L512–517) both need this permission. Check it against your RLS policies with the SQL at the end of this page.
Fix
Revoke UPDATE/INSERT on usage and admin for the authenticated role. Move calling into a Postgres function call_next(queue_id) (SECURITY DEFINER). In one transaction it decrements remaining_tokens where it is above 0, runs queue_position = queue_position + 1, and returns the new row. Only the server should change balances.

HighSYNC-01Two controller devices overwrite each other: token numbers jump backwards and paid tokens vanishMulti-deviceReproduced

The landing page promises calling from “your phone, reception desk, or doctor consultation room with zero lag across screens”. The dashboard never listens for changes, though. Each device sends an absolute number worked out from its own stale copy. It does this for the token position and for the balance.

Steps to reproduce
  1. Log in on two devices (A = reception, B = doctor).
  2. A taps Next three times: token 3.
  3. B still shows “—” and taps Next once.
  4. The token on the TV goes back to 1.
What the test saw
4 calls moved the queue to 1 and charged 1 token (balance 1,499 instead of 1,496). In a second run, a ₹99 recharge on A took the balance to 1,997. One tap on the stale device B then set it to 1,498, so 498 paid tokens were lost.
Fix
Use the server-side call_next() from SEC-01, which increments rather than sets, and render the row it returns. Also subscribe the dashboard to its own queue_details and usage rows so every device stays current.

schema.sql in the project is empty, so your RLS policies and constraints can't be reviewed from the code. Paste this into the Supabase SQL editor. It only reads.

-- 1. Is RLS on, and what does each policy allow?
select tablename, rowsecurity from pg_tables where schemaname = 'public';
select tablename, policyname, roles, cmd, qual, with_check
  from pg_policies where schemaname = 'public' order by tablename;

-- 2. Which unique constraints exist? (DATA-01 needs usage.admin_id unique)
select conrelid::regclass as tbl, conname, pg_get_constraintdef(oid)
  from pg_constraint where connamespace = 'public'::regnamespace;

-- 3. Hosts already hit by the duplicate-row bug
select admin_id, count(*) from queue_details group by 1 having count(*) > 1;
select admin_id, count(*) from usage         group by 1 having count(*) > 1;

A starting point for fix #1:

-- Sketch: one server-side "call next" that charges and advances atomically.
-- Adjust types to your schema. Then remove the client writes to usage/admin.
create or replace function call_next(p_queue_id bigint)
returns queue_details
language plpgsql security definer set search_path = public as $$
declare q queue_details;
begin
  update usage set remaining_tokens = remaining_tokens - 1
   where admin_id = auth.uid() and remaining_tokens > 0;
  if not found then raise exception 'QUOTA_EXHAUSTED'; end if;

  update queue_details
     set queue_position = queue_position + 1, updated_at = now()
   where queue_id = p_queue_id and admin_id = auth.uid()
  returning * into q;
  if q is null then raise exception 'NOT_YOUR_QUEUE'; end if;  -- rolls back the charge
  return q;
end $$;

revoke update, insert on usage, admin from authenticated;
-- client:  const { data, error } = await supabase.rpc('call_next', { p_queue_id: queue.queue_id })
